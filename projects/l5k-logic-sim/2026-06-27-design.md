## 1. Goal

Build an **offline tool that ingests a Rockwell L5K export, interprets the logic,
and simulates it visually** so the logic flow can be validated *before* going
on-site — to cut on-site troubleshooting time (which costs real money).

The experience we're after is the **RSLogix "online" feel, but offline and fed
from an L5K file**: rungs light up as power flows, you can run / single-step the
scan, force tags, and modify logic in the simulated environment.

**Not** the goal: a safety-rated runtime, a perfect 1:1 visual clone of RSLogix,
or hardware-accurate timing. Functional logic equivalence + visibility + the
ability to test and tweak is what matters.

---

## 2. Why this shape (decision log)

The user explored several framings; the final intent and decisions:

- **End use:** offline logic validation before site visits. Drives every tradeoff
  toward "functional equivalence + visibility" over fidelity.
- **Target:** originally floated OpenPLC. Rejected as the *sole* solution because
  **plain OpenPLC does not animate rung power flow or single-step a scan** the way
  RSLogix online does — which is the #1 ask. OpenPLC remains a possible future
  execution backend for correctness cross-checking, but the primary build is a
  **custom interpreter + visual simulator**.
- **Reusable, not project-specific:** the tool should accept *any* L5K. The Briles
  project file is used only as the **coverage benchmark** (a real-world sample of
  what industrial Rockwell code actually contains), not as the thing being built.
- **Chosen approach:** **Approach 2 — custom parser + scan engine + web UI**,
  built **vertical-slice-first** to de-risk a large build.
- **Stack:** **Python** (parser + scan engine; cleanest L5X/L5K parsing story) +
  **a small web UI** (browser-based ladder rendering + animation), engine↔UI over
  a local WebSocket.

### Approaches considered

| # | Approach | Verdict |
|---|----------|---------|
| 1 | Translate L5K → Structured Text → run on OpenPLC as-is | Rejected: no rung animation / single-step; you watch *values*, not *flow*. Misses the core ask. |
| 2 | **Custom interpreter + visual simulator** | **Chosen.** Delivers "see the flow step-by-step + modify in sim." Biggest build → managed via vertical slice. |
| 3 | Hybrid: OpenPLC executes, custom viewer animates | Rejected for now: two synced moving parts, awkward edit story, viewer still has to be built so savings are smaller than they look. |

## 3. Reference benchmark — the Briles file

Parsed `briles_main_rev_023.L5K` (≈12,137 lines, 862 KB) to ground the coverage
target. This is the yardstick, not the deliverable.

- **Controller:** `Sutherland_IPress_CompactGuard`, processor **1769-L30ERMS**
  (CompactLogix safety controller). An i-Press.
- **Scale:** 9 programs, 73 routines, ~1,882 rungs, 24 AOIs, 13 UDTs, 2 tasks, 25 modules.
- **Programs:** `MainProgram`, `Mode_1`–`Mode_4`, `Mode_Supervisor`,
  `Press_Lubrication`, `Lower_KO_Valve_Adapter`, `SafetyProgram`
  → a **mode/state-machine press**, which is very testable offline.

**Instruction frequency (top of the list):**

| Instr | ~Count | | Instr | ~Count |
|-------|--------|---|-------|--------|
| XIC   | 1650 | | JSR   | 67 |
| OTE   | 697  | | NE    | 44 |
| XIO   | 683  | | NOP   | 36 |
| COP   | 407  | | CTU   | 35 |
| MOV   | 355  | | SUB   | 34 |
| OTU   | 237  | | GT    | 33 |
| EQ    | 217  | | ADD   | 30 |
| OTL   | 145  | | GE    | 26 |
| TON   | 107  | | LT/LE | 21/21 |
| ONS   | 96   | | MUL   | 20 |
| LIMIT | 80   | | CPT   | 19 |
| RES   | 73   | | OSF   | 15 |

Plus a long tail: AFI, RIN, GSV (7), CLR, RTO (6), DTOS (5), DIV, INSERT, TOF (3),
SCP, ABS, THRS.

**Takeaway: the bulk is classic discrete + sequencing logic** — exactly the bucket
that simulates cleanly. The hard ~10–20% is AOIs + encoder/HSC + strings/comms.

**AOIs seen (24; mostly small utilities):** `aoi_pulse_feedback_monitoring`,

the **press encoder / high-speed counter** (angle, RPM) — these need a *virtual
encoder* to exercise, since there's no real HSC in the sim.

## 4. Architecture

Four isolated units with clean interfaces:

```
L5K file ──▶ [1] Parser ──▶ [2] IR (JSON) ──▶ [3] Scan Engine ──▶ [4] Web UI
                                                     ▲                  │
                                                     └──── force / step / edit
```

### [1] Parser — `l5k_parser`
Reads the L5K text format. Extracts: controller, programs, routines (rungs),
tags (controller + program scope), UDTs, AOI definitions, task/JSR call structure.
Only parses — never executes. On unrecognized constructs: record a diagnostic with
file location and continue (never hard-fail).
**Interface:** `parse(path) → Project IR`.

### [2] IR — intermediate representation (the durable, reusable asset)
Normalized, engine-agnostic JSON model:
`Project → Programs → Routines → Rungs → Instructions(mnemonic, operands)`,
plus `Tags`, `UDTs`, `AOIs`. This is the contract every other unit depends on and
the thing that makes the tool work on **any** L5K. Versioned schema.

### [3] Scan Engine — `scan_engine`
Deterministic Logix-style scan loop: read inputs → execute routines in order
(following the JSR call tree) → write outputs, against an in-memory tag database.
- One handler per instruction mnemonic.
- Evaluates rung power flow (series/parallel branches → boolean), energizes outputs.
- **Records each instruction's true/false state every scan** (feeds the animation).
- **Free-run and single-step** (one scan or one rung).
- **Tag-force API.**
- AOIs: v1 ships hand-written equivalents for a small set; the rest are stubbed and
  visibly flagged.

### [4] Web UI — `web_ui`
Renders routines as **ladder rungs** (SVG) and **animates them live**: powered
contacts/rails and energized coils highlight each scan. Controls: Run / Pause /
**Single-step** / Reset, tag watch + force panel, program/routine navigator.
Talks to the engine over a local **WebSocket** streaming tag + rung state each scan;
user actions (step, force, edit a value) go back the other way.

### Data flow (one line)
`L5K → Parser → IR → Engine loads IR & builds tag DB → each scan computes
instruction states → streams to UI → UI animates rungs; user step/force/edit → engine.`

## 5. v1 scope — the vertical slice (ruthless YAGNI)

**In:**
- **One mode** from Briles: `Mode_1` + minimal `Mode_Supervisor` glue + any routines
  it `JSR`s into.
- **Instruction set:** `XIC, XIO, OTE, OTL, OTU, ONS, OSF, AFI, NOP, TON, RES, CTU,
  MOV, COP` (simple/scalar), `JSR`, compares `EQ/NE/GT/GE/LT/LE/LIMIT`,
  math `ADD/SUB/MUL/DIV/CPT`.
- Ladder rendering + per-scan animation + run/single-step + tag force.
- **Edit-in-sim (light):** force/toggle tags, disable a rung (AFI), edit
  operand/constant values — live and immediate.

**Explicitly out of v1** (stubbed and *visibly flagged*, never silently dropped):
- HSC/encoder AOIs (`EncoderPuls_to_RPM`, `Pulse_Angle`, `Pulse_Generator`,
  `HSC_Compare`) and the other AOIs.
- UDT-heavy `COP`, strings (`DTOS`/`INSERT`/`Scroll`), `GSV`, `MSG`,
  produced/consumed tags, safety-rating.
- Graphical rung *surgery* (adding/moving contacts) — value/force editing only in v1.

## 6. Error handling

- **Parser:** unknown construct → diagnostic (file location + text) + continue.
  Emits a **coverage report**: % rungs fully parsed + a list of every unsupported
  instruction/AOI encountered.
- **Engine:** unsupported instruction → rung renders as **"unsupported"** (greyed,
  labeled), scan continues. One bad rung never crashes the scan.
- **Determinism:** fixed scan order; timers run off a configurable **simulated scan
  clock**, not wall-clock — so a run is perfectly repeatable.

---

## 7. Testing strategy (TDD throughout)

- **Parser:** unit tests on small L5K snippets → expected IR; one golden-file test
  against a real Briles routine.
- **Engine:** per-instruction truth-table tests (XIC/XIO/OTE, TON timing across N
  scans, CTU counting, ONS/OSF one-shots); rung-level series/parallel branch tests.
- **Integration:** load `Mode_1`, drive a **scripted input sequence**, assert
  expected output tags scan-by-scan. This doubles as a **logic regression test** —
  itself one of the wanted outcomes.
- **UI:** lighter — smoke test that the state stream renders and step/force
  round-trips.

---

## 8. Coverage roadmap (Briles = the yardstick)

Track **"% of Briles rungs/instructions/AOIs covered"** as the expansion metric.
After the v1 slice proves the experience, widen outward in priority order:

1. Remaining discrete / timer / counter edge instructions (TOF, RTO, CTD, OSR, etc.).
2. Simple utility AOIs (`min_dint`, `max_dint`, `scaler_dint`, `LIM_INT`, `SCP`).
3. Encoder / HSC with a **virtual encoder driver** (angle, RPM, pulse generation).
4. The rest (strings, `GSV`, `MSG`, safety) — only if they earn their keep.

---

## 9. Open questions / future

- **Own repo:** if this grows past a parked folder, migrate to a standalone repo so
  it isn't entangled with the Superpowers fork.
- **OpenPLC as a cross-check backend:** optionally emit Structured Text from the IR
  later, to validate engine results against a mature IEC runtime.
- **L5X vs L5K:** v1 targets L5K (text). L5X (XML) is an easier parse and a likely
  early addition — the IR is designed to make the front-end source format swappable.
- **Editing depth:** graphical rung editing (add/move/delete contacts) is a deliberate
  post-v1 item.

```bash
git fetch origin
git checkout project/l5k-logic-sim
cd projects/l5k-logic-sim
python3.11 -m venv .venv && .venv/bin/python -m pip install -U pip pytest
.venv/bin/python -m pytest          # confirm the suite is green
# read this doc + README.md; the Briles L5K is the coverage benchmark (kept locally, not committed)
```

**Baseline decided 2026-06-27:** Python **3.11** (not the macOS system 3.9). Use
`python3.11` explicitly; the `.venv/` is git-ignored and recreated per laptop.
